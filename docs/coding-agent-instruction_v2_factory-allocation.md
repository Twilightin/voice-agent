現行の目的関数は2段階の辞書式と記載されている:
1. 第1優先 = 未充足ギャップの**期間トータル**最小化
2. 同点なら限界利益最大化

## 4. Phase C: 月別ギャップの可視化（全シナリオ共通・並行実施可）

**シナリオ判定に関わらず必要。** Phase A の報告と並行して着手してよい。

### 目的

現在は期間トータルのギャップしか出力されないため、年間ネット −0.15% と表示され、26-03〜05 の未充足が見えない。改善を測る基準線を作る。

### タスク

#### C-1. 月別ギャップを算出・出力する

既存の期間トータルギャップは**変更せず**、追加指標として計算する。

```
月別ギャップ[p][m] = max(0, 要生産[p][m] − 生産回答[p][m])
月別ギャップ合計   = Σ_p Σ_m 月別ギャップ[p][m]
```

期間トータルとの違いは `max(0, ·)` と `Σ` の適用順序のみ。超過生産による相殺が起きない。

参考: SKU `3044` の実データでは、期間トータル 2,411 に対し月別合計 24,111。

#### C-2. 未充足の継続期間を算出する

```
繰越残[p][m] = max(0, 繰越残[p][m-1] + 要生産[p][m] − 生産回答[p][m])
```

26-03 の不足が 26-06 まで解消しない場合、繰越残が4か月分計上され、遅延の長さが可視化される。

#### C-3. 工場別の内訳を出力する

**本案件の中心が工場間配分であるため、これを必ず含めること。**

SKU × 月 × ライン のマトリクスで以下を出力する:

- 要生産（工場別に与えられている場合は工場別、そうでなければ SKU 合計）
- 生産回答
- 稼働可能時間 / 実使用時間 / 稼働率
- 月別ギャップ
- 繰越残

#### C-4. 納期割れ件数

```
納期割れ件数 = Σ_p Σ_m [月別ギャップ[p][m] > 0]
```

量ではなく件数。満杯月に大容量 SKU が優先され小容量 SKU が当月0に落ちる挙動（`_ConstructInitialSolution.py:40-51, 103-169` の貪欲構築の割当順に起因すると記載）の影響把握のため。

### 受入基準

- [ ] **既存の最適化結果（生産回答）が変更前と完全に一致すること。** 目的関数・制約を一切変更していないため、解が変わってはならない
- [ ] 期間トータルギャップの既存出力値が変わらないこと

## 5. Phase D: 目的関数の改修（S3 の場合、または S2 解除後も未充足が残る場合）

**Phase A・C の結果を見てから着手する。独断で開始しないこと。**

### D-1. 標準形との差分

いま扱っている問題は **CLSP with backorders（backlog 付き能力制約付きロットサイジング）** という確立した定式化に対応する。標準形の目的関数は、資源制約下で以下の合計を最小化する:

- 生産費（変動費）
- 段取り費
- 在庫保管費
- **backorder（backlog）費**
- 残業・外注コスト（能力源が複数ある場合）

制約の中核は **品目別・期間別の在庫バランス制約**で、backorder 量が翌期に繰り越される。

**現行実装に欠けているのは以下の2点で、両者は対になっており片方だけでは機能しない。**

1. 月別の在庫バランス（期間合計しか持っていない）
2. backlog コスト項（遅れ残という変数自体が存在しないため、コストを乗せる対象がない）

### D-2. 追加する状態変数と制約

```
在庫[p][m]   ≥ 0    月末在庫残高
繰越残[p][m] ≥ 0    月末未充足残高（backlog）

在庫[p][m] − 繰越残[p][m]
    = 在庫[p][m-1] − 繰越残[p][m-1] + 生産回答[p][m] − 要生産[p][m]
```

両方にコストが乗るため、最適解で同時に正になることはない。相補性制約を明示的に書く必要はない。

**既存の在庫変数がある場合は流用すること。** Phase A の調査結果に従う。

### D-3. 遅延の扱い：2つの方式

**方式1（サービス制約型・推奨）**

実務ではこちらが主流である。backorder コストは直接費と間接費に分解でき、間接費（顧客の信頼の喪失、企業イメージの毀損）の金額化は長年未解決の問題とされている。このため、管理者はコストを指定するよりも目標フィルレートのようなサービス制約を設定することを好む、という指摘が40年以上続いている。

```
minimize   生産費 + 段取り費 + 在庫保管費 + 輸送費
subject to 月別充足率[p][需要地][m] ≥ 目標値
```

**制約の粒度に注意すること:**

| 粒度 | 可否 | 理由 |
|---|---|---|
| SKU × ライン × 月 | **不可** | 応援生産・工場間配分を禁止してしまう |
| SKU 合計のみ | **不可** | 地域欠品が他地域の過剰で隠れる |
| SKU × 需要地 × 月 | 可 | 納期の約束と一致する |
| SKU × 得意先 × 月 | 可 | より正確 |

**需要側だけを縛り、供給側（どの工場で作るか）は自由にする。** これにより工場間配分が制約違反にならず、かつ東日本の欠品が西日本の過剰で隠れることもない。

前提として、要生産データが需要地または出荷先の情報を持っている必要がある。Phase A-1 で確認すること。持っていない場合、この粒度では書けないため方式2を検討する。

**方式2（ペナルティ型）**

社内に充足率の基準が存在しない場合に採る。ただし**線形ではなく階段型にすること。**

```
線形:  遅延費 = 単価 × 個数 × 月数
  → 「1個を7か月待たせる」と「7個を1か月待たせる」が同点になり、感覚と合わない

階段型:
  許容ウィンドウ ω 以内の遅れ  →  ペナルティ 0
  ω を超えた遅れ               →  固定の大きなペナルティ（超過月数に依らず一定）
```

顧客が許容可能な待ち時間 ω 以内に受け取ればペナルティは発生せず、それを超えると相当額の固定ペナルティが発生し、追加待ち時間が伸びても増えない——という形が産業界との協働から出てきたモデルとして報告されている。「何か月遅れたか」より「割れたかどうか」が効く構造で、納期割れの実感に近い。

区分線形で単調増加なら凸関数になるため、**バイナリ変数なしで LP のまま表現できる。**

313 の遅延は1〜3か月なので、ω = 1 か月に置けば 2か月超の分のみがペナルティ対象になる。

### D-4. 単価の決め方（方式2の場合）

絶対額ではなく**比**が挙動を決める。

```
遅延費 ÷ 在庫保管費  =  何か月前まで作りに行くか
段取り費 ÷ 在庫保管費 =  何か月分をまとめて作るか
```

前者だけ調整して後者を無視すると、**机上では能力が足りるのに実行段階で段取り時間が乗って足りない解**が出る。前倒しで新しい月に品目を流すと段取りがまるごと増える点に注意（26-01 の段取りは 3,360 分、26-05 は 840 分と月により4倍違う）。

### D-5. やってはいけないこと

- **前倒し窓（`pre_production_months`）の値・制約式の変更。** 窓は賞味期間と納品期限（1/3ルール）から逆算した値と整合しており、正しい可能性が高い（マヨネーズ13カ月 × 1/3 − 各種マージン ≈ 2か月、ノンオイルドレッシング9カ月 × 1/3 − 各種マージン ≈ 1か月）。実値 `55529`=1・他=2 と一致する。窓の緩和は得意先の納品期限運用の確認と商談を伴う経営判断であり、コードで先行してはならない
- 窓を「在庫消化期限」型に書き換えること。**元の窓より緩くなり、賞味期限違反の在庫を生む**
- 期初在庫の 0 固定を勝手に実在庫に差し替えること（セクション 6 参照）
- 納期割れ件数のバイナリ変数を目的関数に追加すること（MIP 化し解時間が大幅に増える。後続フェーズとする）
- `_ConstructInitialSolution.py` の貪欲構築ロジックの変更（別件として切り出す）

### D-6. 受入基準

## 6. 本指示書のスコープ外（気づいた点は報告のみ）

### 6-1. 期初在庫と IBP 連携

調査ドキュメントに「初期在庫が 0 固定・IBP の `PROJECTEDINVENTORY` / `DEPENDENTDEMAND` がエンジンに投入されていない」との記載がある。事実なら、要生産は正味所要ではなく総所要であり、**現在 100% 充足している月が実在庫を考慮すると過剰生産になっている可能性がある。**

本来はギャップの定義を精緻にする前にギャップの入力を確定させるべきだが、データ連携の変更は影響範囲が大きいため別タスクとする。

### 6-2. 貪欲構築の割当順

満杯月に大容量 SKU `55529` が優先的に能力を取り、小容量の `3044`・`41228` が当月 0 に落ちる挙動（`_ConstructInitialSolution.py:40-51, 103-169`）。目的関数とは独立した問題。

### 6-3. 窓の導出ロジック化

窓を商品マスタの固定値ではなく「賞味期間 × 納品期限係数 − 年月表示の丸め損 − 物流LT − 安全マージン」から導出する形にリファクタする余地がある。ただし得意先の納品期限運用（1/3 か 1/2 か）の確認が前提。

### 6-4. 工場 × 需要地で窓が変わる論点

遠方の工場から応援すると輸送時間が納品期限の持ち時間を消費するため、実効窓が縮む。工場間配分を増やす方向に最適化するなら無視できないが、現状の確認（A-5）のみ行い、実装は別タスク。
